# Fresh Market 后端接口使用说明（C端秒杀）

> 本文档面向前端开发，描述用户端秒杀的 5 个接口与下单规则（商品 3 个 + 订单 2 个）。秒杀下单链路 **2026-09-03 实测通过**，订单分页/支付 **2026-09-04 实测通过**（含 WebSocket 来单提醒推送），示例为真实响应。
> 通用约定与《user端接口使用说明.md》一致：统一响应 `{code, msg, data}`、时间字段格式 `yyyy-MM-dd HH:mm`（无秒）、跨域走 dev server 代理。

## 1. 鉴权

秒杀用户端接口**全部需要登录**（`/user/**` 拦截）：

- 请求头：`authentication: <登录返回的 token>`（注意不是管理端的 `token` 头）。
- 未带/无效 token：**HTTP 401，响应体为空**。
- 秒杀下单自动绑定当前登录用户，一人一单（见 2.3 规则）。

## 2. 接口详情

### 2.1 在售秒杀商品分页

`GET /user/seckill/pageOnSale`（需 token）

| 参数 | 类型 | 必填 | 说明 |
|---|---|---|---|
| page | number | 是 | 页码 |
| pageSize | number | 是 | 每页条数 |
| name | string | 否 | 商品名称（模糊查询） |

成功响应（真实示例）：

```json
{
  "code": 1,
  "msg": null,
  "data": {
    "total": 1,
    "records": [
      { "id": 10, "name": "限时秒杀红富士苹果", "seckillPrice": 5.99, "stock": 100,
        "limitNum": 2, "startTime": "2026-09-03 00:00", "endTime": "2026-09-03 23:59",
        "status": 1, "createTime": "2026-09-03 11:56", "createUser": 1,
        "updateTime": "2026-09-03 11:57", "updateUser": 1 }
    ]
  }
}
```

**规则**：只返回**启用**（status=1）的秒杀商品，禁用的不会出现（即使传 `status` 参数也会被后端忽略）。**列表可能包含尚未开始或已结束的活动**——是否处于秒杀时段由 `startTime`/`endTime` 决定，前端用这两个字段做倒计时与按钮状态（未开始显示"即将开始"，进行中显示"立即抢购"，已结束显示"已结束"）。

### 2.2 查询秒杀商品详情

`GET /user/seckill/get`（需 token）

| 参数 | 类型 | 必填 | 说明 |
|---|---|---|---|
| id | number | 是 | 秒杀商品 id |

成功响应：data 为商品对象（字段同 2.1 records 内的结构，**不限状态**，禁用的商品也能查到，前端注意按 `status`（是否启用）和 `startTime`/`endTime`（是否在时段内）控制按钮）；id 不存在时 `data: null`。

### 2.3 秒杀下单

`POST /user/seckill/seckill`（需 token，JSON）

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| seckillGoodsId | number | 是 | 秒杀商品 id（DoSeckillDTO） |

```json
{ "seckillGoodsId": 13 }
```

成功响应（2026-09-03 实测）：

```json
{ "code": 1, "msg": null, "data": null }
```

失败响应（均为 `code: 0`，msg 见下表）：

| msg | 场景 |
|---|---|
| `"商品不存在"` | id 无效 |
| `"秒杀商品已禁用"` | 商品 status=0（2026-09-03 实测：在时段内、已预热仍会被拦截） |
| `"不在秒杀时间内"` | 当前时间不在 startTime–endTime 内 |
| `"库存不足"` | Redis 库存已扣完，**或商品未做缓存预热**（见下方规则 4） |
| `"已经购买过了"` | 该用户已秒杀过此商品（一人一单） |

**下单规则**：

1. **下单前置校验**：商品存在 → 已启用（status=1）→ 在 startTime–endTime 时段内，任一不满足直接失败（对应上表前三行）。
2. **一人一单**：同一用户对同一秒杀商品只能成功下单一次，重复请求返回"已经购买过了"。
3. **库存判定在 Redis 中原子完成**（lua 脚本：判库存 + 判重复购买一体），高并发下不会超卖。
4. **依赖管理端预热缓存**：秒杀库存来自 Redis key `fresh:seckill:stock:<id>`，由管理端《seckill管理端接口使用说明.md》2.4 修改接口写入。商品未预热时秒杀一律返回"库存不足"——联调时发现该提示但数据库明明有库存，先确认管理端是否调用过修改接口。
5. **下单成功 ≠ 订单立即入库**：订单先发 RabbitMQ，由后端消费者异步写入数据库（正常毫秒级）。**成功响应里没有订单号/订单 id**，下单成功后调 2.4 轮询/刷新自己的订单列表（间隔 1 秒左右即可拿到）。
6. 秒杀订单初始状态为 **1 待付款**，通过 2.5 填写收货地址并支付后流转为 **2 待接单**。

### 2.4 分页查询自己的秒杀订单

`GET /user/seckillOrders/page`（需 token，2026-09-04 实测）

| 参数 | 类型 | 必填 | 说明 |
|---|---|---|---|
| page | number | 是 | 页码 |
| pageSize | number | 是 | 每页条数 |
| status | number | 否 | 订单状态 1待付款 2待接单 3已接单 4派送中 5已完成 6已取消 |

成功响应（真实示例）：

```json
{
  "code": 1,
  "msg": null,
  "data": {
    "total": 1,
    "records": [
      { "id": 6, "number": "2026090400000004", "seckillGoodsId": 13, "status": 1,
        "userId": 35, "orderTime": "2026-09-04 10:29", "payStatus": 0,
        "seckillGoodsName": "支付测试甜橙" }
    ]
  }
}
```

（省略部分 null 字段，完整字段同《seckillOrders接口使用说明.md》第 2 章表格。）

**规则**：
- **只能查到自己的订单**（按登录用户隔离，实测他人订单不可见）。
- 每条记录多带 `seckillGoodsName`（秒杀商品名称，商品被删时为 null）。
- 按订单 id 倒序（最新在前），适合"抢购成功后刷新拿订单号"的场景。

### 2.5 秒杀订单支付（填写收货地址并支付）

`PUT /user/seckillOrders/payment`（需 token，JSON，2026-09-04 实测）

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| number | string | 是 | 订单号（从 2.4 获取） |
| addressBookId | number | 是 | 收货地址 id（地址簿接口拿到的 id，须是当前用户自己的地址） |
| payMethod | number | 是 | 支付方式 1微信 2支付宝 |

```json
{ "number": "2026090400000004", "addressBookId": 3, "payMethod": 1 }
```

成功响应：`{ "code": 1, "msg": null, "data": null }`

失败响应（均为 `code: 0`）：

| msg | 场景 |
|---|---|
| `"订单不存在"` | 订单号无效，**或订单不属于当前用户** |
| `"收货地址不存在"` | 地址 id 无效，或用了别人的地址 |
| `"订单已取消或已支付"` | 对已支付/已取消订单再次发起支付 |
| `"请勿重复支付"` | 并发重复支付（分布式锁拦截） |

**支付规则**：
- 一次调用完成两件事：**用地址簿快照收货信息**（consignee/phone/address 写入订单，addressBookId 一并记录）+ **完成支付**（status 1待付款→2待接单、payStatus 0→1、记录 checkoutTime）。
- 实测数据变化：`consignee=张三, phone=13900000001, address=北京市朝阳区…, status=2, payStatus=1, checkoutTime=2026-09-04 10:30`。
- 支付成功会**通过 WebSocket 向商家端推送来单提醒**（与普通订单一致，实测消息：`{"orderId":8,"type":1,"content":"订单号：2026090400000006"}`，对接方式见《orders接口使用说明.md》第 5 章）。
- 目前为模拟支付（未接微信/支付宝），调接口即支付成功。

## 3. 联调注意事项

- 秒杀商品与普通商品（goods 表）是两套体系：秒杀商品来自管理端单独配置，不在普通商品列表/分类接口中出现。
- 秒杀接口对并发敏感，联调压测时注意：库存扣减分两步——下单时实时扣 Redis（`fresh:seckill:stock:<id>`），订单落库时在同一事务扣数据库库存（略滞后）；订单条数以数据库 `seckill_orders` 表为准，Redis 与数据库短暂不一致属正常（异步落库）。
- 管理端删除秒杀商品后，用户端 2.1/2.2 查不到该商品，但已产生的订单仍在（2.4 与管理端订单分页均可见，商品名显示为空）。
- 秒杀订单与普通订单是两张表：2.4/2.5 只操作秒杀订单，与《orders接口使用说明.md》的普通订单互不相通；推荐下单流程：秒杀（2.3）→ 刷新订单列表拿订单号（2.4）→ 填地址并支付（2.5）。
